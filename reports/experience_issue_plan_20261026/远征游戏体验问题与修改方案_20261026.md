# 远征游戏体验问题与修改方案

2026 年 10 月 26 日　问题评审与后续实施方案

本轮整理 9 组反馈。建议先修复背包滑动这一操作问题，同时确定界面层级规范；商城和活动页按展示型页面重新设计。世界画面先做采样对比和比例标尺，再调整景物，最后把大地图、骑行到达与垂钓入口连成完整体验。

本轮交付为问题梳理、设计要求、实施顺序和验收条件。附件中“生成参考图”“去掉过滤”“修改”等表述作为后续方案输入，本次不执行图像生成、游戏修改或打包。

## 二 逐项问题与修改方案

### Q01 荣誉商城需要商品展览结构和多品类扩展能力

**问题与影响**

图 01 是荣誉商城。首屏主要由标题、荣誉余额和两列纸质商品卡组成。各卡重复使用图标、名称、数量、价格和“查看商品”按钮，卡片内留白较多，缺少主题展示、分类组织和商品之间的视觉差异。用户可以看到商品，但页面更像兑换清单；未来种类增加后，浏览成本会明显上升。

“成熟商城”应落实为清楚的信息层级、合适的展示密度、可靠的交易流程和可扩展的品类结构。本次不把这一诉求扩大为充值、抽卡、限购或折扣等新商业规则。

**当前实现与缺口**

当前 `HonorMarketPanel.gd` 从 `exchange.json` 读取 5 件商品，已有可滚动网格、窄屏列数适配、商品详情及确认兑换。兑换逻辑已有余额检查、防重复处理和存档失败回滚，不能写成“商城没有详情或交易保护”。

需要扩展的重点有两层：展示上，所有商品共用单一纸卡；数据上，奖励处理目前面向 `item_` 物品，用途说明也有硬编码。未来若加入外观、坐骑或组合奖励，单纯多放几张商品卡不能完成业务适配。

**拟修改方案**

1. 首屏按“标题与余额 → 主题展示 → 分类导航 → 商品展区”组织。主题区说明当前商城定位并展示重点商品，不用大横幅挤压商品浏览区域。
2. 当前材料与宝石采用紧凑卡片，优先露出图标、名称、数量、价格和可兑换状态；减少每张卡相同的大块空白。
3. 分类由实际商品数据生成。没有商品的分类不展示，不先摆出大量空入口。
4. 为不同品类预留展示模板：材料和宝石用网格；未来外观或坐骑用较大预览；组合商品用内容清单。这里只预留能力，不承诺本轮新增这些商品。
5. 保留“浏览 → 详情 → 确认兑换 → 结果反馈”的链路。详情包含实际用途、获得内容、价格和持有量；兑换成功后同步刷新余额与库存。
6. 商品类型、展示模板、用途说明与奖励发放类型分别配置，新增品类时逐项校验。展示价格、确认价格和最终扣款使用同一有效价格来源。
7. 根据安全区和可用宽度适配布局；返回入口和余额保持可见，商品区域独立滚动。

**验收条件**

- 现有 5 件商品均可找到、查看详情并完成兑换，原有用途和奖励不改变。
- 使用至少 20 件测试商品覆盖长名称、大数量、不同展示模板，首尾可达，无卡片裁切或按钮错位。
- 有余额不足、加载失败、商品为空、兑换中和兑换失败的明确状态。
- 连续点击确认不重复扣款；保存失败时余额与奖励保持一致；关闭详情后返回原浏览位置。
- 未配置奖励处理的品类不能进入可确认兑换状态，避免“图上能买、实际不能发放”。

**拟涉及入口**　`src/ui/HonorMarketPanel.gd`、`data/exchange.json`、商城所用的阅读与商品展示组件。详见证据 C01。

### Q02 活动页需要从文字公告升级为可浏览的活动中心

**问题与影响**

图 02 只有两张相似的活动卡，主要展示标题、说明和“进行中”。玩家难以迅速判断活动亮点、参与后获得什么、下一步在哪里。顶部横幅可见模糊表现，但不能仅凭截图认定为资源损坏或加载错误；该区域需单独检查原始素材和缩放方式。

**当前实现与缺口**

活动页已有时间状态、活动详情和前往玩法的能力，当前配置是两项常驻内容。改版应增强浏览和参与体验，不是重新搭建一套空壳活动系统。

**拟修改方案**

1. 上部放置清晰的活动主题图和简短说明；内容区展示活动卡。每张卡应能回答“是什么、当前能否参与、有什么实际收益、如何进入”。
2. 常驻与限时活动采用有区别的状态表达。仅配置了起止时间的活动显示倒计时，常驻活动不伪造剩余时间。
3. 预留活动分类或状态筛选；只有两项活动时可保持简单，避免空分类比内容还多。
4. 奖励预览、参与条件、进度、领取状态从真实玩法数据取得。没有对应逻辑时，先明确接口，不做虚假的“可领取”提示。
5. 卡片入口、详情入口与“前往”保持一致，未开放时说明解锁条件或开放时间。
6. 按“结构草图 → 参考图 → 可复用元素拆解 → 游戏内样板 → 真机评审”推进视觉设计。参考图中的文字、按钮和状态需要转成真实控件，不能用一张整图代替交互页面。

**验收条件**

- 无活动、仅一项、多项、未开放和已结束时，页面均完整可用。
- 首页能辨认主题、状态和参与入口；长标题、长说明不会遮挡按钮。
- 活动详情与玩法页的奖励、条件和状态一致，打开页面不会误改变进度或领取状态。
- 顶部主题图在目标屏幕上清晰，无明显拉伸、模糊补带或文字与图片内容重叠。
- 现有两项活动仍能从活动页进入正确玩法。

**拟涉及入口**　`src/ui/ActivityPanel.gd`、`data/activities.json` 及活动主题素材。详见 C02。

### Q03 人物与背景风格需要先做采样对比再定方向

**问题与影响**

图 03 中，人物、坐骑与地面和建筑的细节密度、边缘表现不同，存在拼接感。用户提出“先尝试去掉背景像素过滤”是合理的对比方向，但目前不能断言去掉后就能统一画风。

**当前实现与缺口**

背景的最近邻采样分散在普通背景、参考底图、景物和地形材质中；角色还使用独立材质处理。项目默认过滤不是唯一入口。另一方面，素材本身已经形成的像素颗粒、笔触与光影，不会因更换采样方式自动恢复或统一。

**拟修改方案**

1. 先建立采样清单，分别记录地面、建筑、景物、水面、人物、怪物和 UI，明确哪些来自节点过滤、哪些来自材质、哪些已烘焙进素材。
2. 选择城市、雪地野外、水岸三组固定机位。第一轮只比较背景和景物的原采样与平滑采样，保持人物、镜头、色调和位置不变。
3. 若平滑采样只能让背景变糊，第二轮再比较原始高清底图或同风格替代素材；避免不断叠加滤镜掩盖素材差异。
4. 从边缘清晰度、细节密度、色彩、光照方向和地面接触感共同评审，不能只检查静止截图“是否柔和”。
5. 选定样板后再制定角色与环境的共同风格标准，并将 Q04 的比例校准放在该标准下完成。

**验收条件**

- 对照图记录相同设备、画面尺寸、机位和采样差异，能单独判断过滤的作用。
- 静止和连续移动都检查：角色轮廓清楚、地面不明显闪烁、景物边缘无新增白边，UI 与文字清晰度不受影响。
- 保留原采样基线和对照结论，确认样板后才推广至更多地图。
- 最终风格不能依靠“把所有内容变模糊”来消除差别。

**拟涉及入口**　`project.godot`、`MapScene.gd`、`ReferenceFloor.gd`、`ReferenceWorldArt.gd`、`ReferenceTerrain.gd`、`SunnyTravelArt.gd`、角色专用材质。详见 C03。

### Q04 人物 坐骑 怪物与景物需要统一比例标尺

**问题与影响**

图 04 至图 05 结合文字反馈，反映出上马后人物显得变大、步行人物及部分怪物偏小、地图较空旷的问题。这些属于不同层级的尺度关系，不能只给所有对象乘一个放大倍率。

图 04 与图 05 来自不同地图，不能直接按截图像素测得严格的上下马比例。最终应在同一场景、同一位置和同一镜头下对照。

**当前实现与缺口**

步行角色会读取地图的 `player_scale`，多张地图使用 0.54，部分城市使用 0.65 或 0.66；骑乘时则切换成人马合成图集，并使用固定缩放。两者需要按实际可见身体大小校准，不能只比较节点的缩放数字。

怪物既有目标高度，也有宽度上限；宽体怪可能因宽度限制再次缩小。景物另有尺寸配置，具备局部调整条件。这里已找到清楚的调整入口，但尚未得到应全局采用的倍率。

**拟修改方案**

1. **建立标尺**：按去除透明边后的可见轮廓，记录角色站立身体高度、骑乘时骑手身体高度、马体高度、普通怪与首领体量、门洞与道路宽度。为代表性对象制作同屏对照。
2. **先校准上下马**：允许人马组合总高增加，骑手自身不应明显膨胀。合成素材若骑手与马体比例有误，应回到素材校准，不能单纯缩小整个人马组合。
3. **再评审人物稍大方案**：保持背景范围和镜头基线，试做小幅角色尺寸对照；选定后同步检查武器、阴影、脚点、名牌、遮挡及交互提示。
4. **怪物按类别校准**：区分小型生物、普通人形、精英和首领。检查宽体怪的限制；不要求所有怪物与人物一样高，也不单靠等级决定大小。
5. **局部处理空旷感**：先检查道路两侧视觉锚点、景物分组和功能点周围密度，再考虑少量景物放大。保留必要的战斗空间与道路辨识，避免用随机堆物填满画面。
6. **同步校准可走空间**：放大景物时复查视觉边界与碰撞边界；角色变大时检查骑乘通过窄路、门洞和桥梁的表现。视觉尺寸与碰撞范围分别核对，不机械同步放大。

**验收条件**

- 三职业、步行与已开放坐骑、四方向均有同机位对照，骑手身体比例稳定，脚底与阴影贴地。
- 城市、窄路和首领区域都检查上下马、转向、贴墙、过门、树后遮挡及进入玩法点。
- 放大后角色不被名牌遮住，武器不离手，怪物的体量与威胁辨识更清楚。
- 景物调整后道路仍清楚可走，交互点不被盖住，不出现“看似能过但被挡住”的新增问题。
- 比例参数在样板确认后锁定，再批量应用；本方案不预先规定全局放大百分比。

**拟涉及入口**　`data/main_world_maps.json`、`MapScene.gd`、`MountVisual.gd`、`MonsterArt.gd`、`data/monster_art.json`、景物清单。详见 C04。

### Q05 背包滑动受阻应作为首个操作修复项

**问题与影响**

用户明确反馈物品不能上下滑动。图 06 显示材料列表底部还有未完整露出的物品，若无法滚动就会直接阻断浏览与选择，应先于大规模视觉改版处理。

**当前实现与待查原因**

背包已有 `ScrollContainer` 与动态网格。公共组件隐藏滚动条的设置不等于禁用滚动，不能据此直接认定原因。

需要排查的路径包括：物品格是否拦截拖动、触控拖动阈值是否合适、滚动内容高度是否正确、手势过程中是否刷新列表，以及焦点自动定位是否把列表拉回。当前选中与刷新会涉及列表重建和焦点可见性处理，是重点排查入口，但尚不能写成已证实的触摸故障根因。

另有一个独立的静态隐患：焦点上下导航使用固定 5 列步长，而实际列数会变化。该问题应在同一轮检查，不能与手机触控问题混为一谈。

**拟修改方案**

1. 先固定反馈安装包、设备、显示比例、背包分类和物品数量，录制从进入背包到滑动失效的完整过程。
2. 分别从物品图标、格子边框、格间空隙和空白区域开始拖动；记录事件是否到达滚动区、偏移量是否变化，以及是否被刷新或焦点重新覆盖。
3. 确认列表的实际内容高于可视区，外层容器正确限制可视高度，详情区不会遮挡或吞掉物品区的手势。
4. 明确点按与拖动的分界：点按选中物品，拖动滚动列表；滚动过程中不误选、不使用物品、不反复重建列表。
5. 选中、装备、售出或切回页面后保留合理的浏览位置；删除物品后位置不得落在无内容的空白末尾。
6. 可继续隐藏常驻滚动条，但增加轻量滚动反馈或下一行半露提示。键盘与手柄导航改为按实际网格列数计算。

**验收条件**

- 装备、材料、宝石和待领取四类均用超过三屏的数据测试，连续上下滑动能到达首尾。
- 从格子与空隙起手均可拖动，轻点仍能正常选择；快速滑动不触发物品操作。
- 选中、装备、售出和刷新后不无故跳顶，反复开关页面无卡死。
- 不足一屏时不会出现无意义的空白滚动；窄屏与长屏均可正常使用。
- 必须有真机修前与修后录屏，并记录测试包版本，才能标记该问题已修复。

**拟涉及入口**　`src/ui/BagPanel.gd`、`src/ui/ChestPageUI.gd` 和背包物品格的输入处理。详见 C05。

### Q06 字体与按钮需要统一规则并建立主次层级

**问题与影响**

图 07 至图 08 的“归路托付”纸页面中，任务名、简介、完成状态、目标和报酬的字号接近，内容之间又有大段固定留白。玩家较难一眼找到当前任务重点。底部三枚按钮的高度、样式和视觉内边距不一致，使同组导航显得不整齐。

用户所说的“统一字体”与“突出重点”应同时满足：字体家族和使用规则统一，标题、正文、状态与奖励仍须有层次。同级按钮规格一致，也不意味着所有功能的按钮必须同宽。

**当前实现与原因**

对应页面在 `CityScene.gd` 的 `_open_return_job`。任务名字号为 18，其余多项文字为 17，主要依赖颜色区分；内容采用固定位置，已完成时不会生成主操作，却仍保留原操作区空白。

底部“原有事务”“其他托付”均为 120×44，“返回”为 120×38，且使用另一套按钮样式。代码确认的是等宽、不同高度与样式，不能把截图观感直接写成实际宽度不同。

项目中已有多套字体和按钮规则，问题在于各页面覆盖较多、语义层级不一致，不是完全没有规范。

**拟修改方案**

1. 以归路托付、商城和活动页为首批样板，定义页面标题、区块标题、条目名称、正文、状态、辅助说明和数值七类语义角色。
2. 标题用于定位页面；条目名称突出当前对象；状态采用简洁徽标；目标成为阅读主区；奖励以清楚的图标和数值排列。不能只把所有文字一起加粗或放大。
3. 归路托付改为随内容伸缩的纵向布局。已完成状态收起主操作占位，长文本可在内容区滚动，底部导航保持稳定。
4. 按钮分为主操作、次操作、导航返回和页签。同一组按钮使用相同高度、基线、边距与状态规则，主次通过位置和颜色区分。
5. 接取、追踪、交付等任务操作按实际状态展示；“原有事务”“其他托付”“返回”统一为导航组，不与任务主操作争夺注意力。
6. 触控范围按实际手机显示比例验证，不仅看设计稿中的逻辑像素。窄屏必要时改为纵向排列，不通过缩小文字硬塞三枚按钮。

**建议样板字号**

以下仅作为第一轮样板起点，单位为项目逻辑尺寸，需真机确认后再固化为公共规范。

| 文本角色 | 建议起点 | 使用目的 |
| --- | --- | --- |
| 页面标题 | 26 至 30 | 明确当前页面 |
| 区块或任务标题 | 21 至 24 | 突出当前任务和信息组 |
| 正文 | 17 至 19 | 保证连续阅读 |
| 辅助说明 | 15 至 17 | 补充条件与解释 |
| 价格 奖励等关键数值 | 20 至 24 | 快速扫描，不与正文混淆 |
| 按钮文字 | 18 至 20 | 与按钮高度及内边距共同校准 |

**验收条件**

- 归路托付的未接取、进行中、可交付和已完成四种状态均清楚，完成后不保留无意义的大空白。
- 同组底部按钮高度和间距一致，长文案不压缩触控区域；按下、选中和禁用状态可辨。
- 长任务名、长正文、大额奖励与窄屏均不截断关键内容，不出现内容与按钮重叠。
- 相同语义角色跨商城、活动、任务页表现一致，正文不靠花哨字体制造重点。
- 样板确认后形成统一组件，再逐页迁移；页面迁移有清单，避免只修两张截图。

**拟涉及入口**　`src/city/CityScene.gd`、`TravelChestUI.gd`、`InventoryQuestSkin.gd`、`ReadingSkin.gd`、`CraftUI.gd`。详见 C06。

### Q07 骑马动作需要降低播放频率并保留运动连续性

**问题与影响**

用户希望骑马动作更慢、更稳。本项主要来自文字反馈，没有对应动态录屏，因此不能仅凭静态截图判断实际循环速度。需要区分动画播放节奏、角色移动速度和游戏整体帧率。

**当前实现与缺口**

当前图集设有待机、步行和奔跑的独立帧段，基准播放速度分别为 5、9、15；运行时还会按移动状态叠加速度倍率。若只改基准值，部分速度下仍可能显得过快。蹄声与接触帧存在关联，节奏调整需一起核对。

**拟修改方案**

1. 保留原始帧序列，先调整动画播放参数，不降低游戏整体帧率，也不通过随意抽帧让动作变卡。
2. 先做原节奏、约慢 15%、约慢 25% 三组对照。百分比只是试验档位，不是已确定参数。
3. 分别评审待机、慢走和奔跑；角色移动速度先保持一致，便于判断动作频率本身。
4. 检查基准速度和运行时倍率共同作用，避免高速状态把已减慢的动画再次推得过快。
5. 同步校对落蹄、蹄声、身体起伏和方向切换；若慢播后明显滑步，再调整步幅或动画节奏，不直接改变玩法速度掩盖问题。

**验收条件**

- 同设备、同路段、同位移速度录屏对比，动作更舒缓且走跑有明确区别。
- 四方向与斜向切换连续，低速摇杆不抖动，停止后正常进入待机。
- 蹄声与落地相符，没有因减速造成明显滑步或停步后继续踏步。
- 骑行速度、碰撞和目的地到达判定符合原玩法要求。

**拟涉及入口**　`src/world/MountVisual.gd`、`MapScene.gd` 的骑乘动作和音效同步。详见 C07。

### Q08 垂钓需要专属场景和完整的阶段反馈

**问题与影响**

用户希望垂钓等玩法更精致，进入独立界面。本项没有专门截图；源码确认已有 `FishingPanel`，因此需求应理解为把现有弹窗升级为完整的专属玩法呈现。

当前垂钓以小型遮罩弹窗、通用鱼图和判定条为主。虽已有抛竿、收竿、剩余次数、图鉴和相关结算，但环境感、过程表现和结果反馈仍比较简单。

**拟修改方案**

1. 第一阶段做专属全屏垂钓界面：主视觉是水域、角色和浮漂；主操作位于易触达位置；规则与剩余次数作为辅助信息。
2. 明确“准备 → 抛竿 → 等待 → 咬钩 → 收竿判定 → 结果”的阶段，每阶段用动画、声音和简短提示说明发生了什么。
3. 展示对应钓点的地点名、水域外观和实际鱼种，不同区域可共用交互框架、替换环境资源。
4. 成功展示鱼种、数量和实际入包结果；失败说明结果并提供重试；次数耗尽时解释原因，提供返回地图入口。
5. 首轮保留既有产出、次数和核心判定规则，集中完善表现。张力条、鱼竿、鱼饵、稀有天气等新增规则另列后续提案，不与界面精修捆绑。
6. 与 Q09 的钓点数据共用来源。从现场进入，关闭后回到原钓点；中途退出、后台恢复和结算失败有明确状态处理。
7. 垂钓作为生活玩法样板，后续其他玩法分别评审；不把所有玩法机械套用同一张弹窗。

**验收条件**

- 从真实钓点进入对应水域，地名、鱼种、次数和地图状态一致。
- 各阶段有清楚的视觉与声音反馈，玩家能理解何时需要操作。
- 成功、失败、次数耗尽、中途退出、重新进入和应用切后台均不会重复结算或丢失结果。
- 结果展示与实际背包获得一致；保存失败时给出明确反馈。
- 竖屏单手可操作，按钮不挡浮漂与判定信息，退出后回到原来的地图位置。

**拟涉及入口**　`src/ui/FishingPanel.gd`、`MapScene.gd` 的现场入口，以及现有垂钓数据与结算接口。详见 C08。

### Q09 大地图需要连接玩法图标 真实坐标与现场交互

**问题与目标**

用户希望像 GTA 的地图一样，看到钓鱼等功能标志后，知道去哪里、怎样过去，骑马抵达后能实际开展玩法。这里借鉴的是“功能图标与地理位置连在一起”的体验，不要求复制其美术风格或重建同等规模的开放世界。

**当前实现与缺口**

项目已有地区节点连线、地图拖动与缩放、任务定位、驿车旅行、局部寻路和跨图下一跳。主世界数据也已有带坐标的钓点。因此不能把现状写成没有地图、没有导航或只有一张静态图片。

需要补齐的是：玩法地点在地图中的真实位置、可用状态、地点详情、统一追踪对象，以及从地图选点到骑行到达并现场交互的连续体验。

**拟修改方案**

1. 世界总览保留地区及道路连接；地区详图展示真实地形与道路关系，并按实际位置放置玩法标志。先复用现有结构，不先承诺无缝大世界改造。
2. 建立统一玩法地点记录，复用现有钓点等数据，不在 UI 中再维护一份手工坐标。
3. 首批接入钓鱼、商店、驿站和重要 NPC。提供图例与筛选，近距离标志密集时做避让或聚合，不能用一屏重叠图标代替功能完整。
4. 点击钓鱼标志显示地点、开放条件、可用状态和相关内容，再提供“设为目的地”。距离只在有可靠坐标或路线计算时展示。
5. 设定后，大地图、小地图和实景 HUD 使用同一追踪对象；本地图给出局部引导，跨图按出口关系逐段引导。
6. 手动骑行到达是必须走通的路径；已有自动前往能力可复用，但不把自动寻路作为用户必须接受的移动方式。
7. 抵达真实交互范围后提示进入垂钓，玩家确认才打开界面。点击地图图标不能在远处直接开始钓鱼。
8. 统一地图显示、路线可达和现场交互的开放条件。支持取消追踪、摇杆接管、未解锁、次数耗尽和路线阻断等反馈。

**玩法地点的最小数据要求**

| 字段 | 用途与约束 |
| --- | --- |
| 唯一标识 | 地图标志 追踪目标与现场交互共用，切图后仍能识别同一地点 |
| 类型与地区 | 决定图标 图例筛选和所属地图 |
| 世界坐标与交互范围 | 标志位置 路线终点和现场触发使用同一来源 |
| 名称与说明 | 显示地点内容，不能用技术 ID 代替用户可读名称 |
| 开放条件与当前状态 | 同一判定同时供地图 导航与现场入口使用 |
| 到达后的操作 | 连接垂钓 商店或 NPC 的真实入口 |

**必须走通的完整用例**

打开地图 → 找到钓鱼标志 → 查看地点与可用条件 → 设为目的地 → 关闭地图 → 骑马沿道路前往 → 必要时跨图并继续追踪 → 到达正确水边 → 确认进入该钓点的垂钓界面 → 退出后返回现场。

**验收条件**

- 当前地图、相邻地图、需要多次跨图的钓点各走通一次，图标与实际水边位置一致。
- 地图拖动和缩放后标志仍对齐，拖地图不误选地点，关闭地图不丢失追踪。
- 取消追踪后，路线、HUD 和小地图标志同步清除；切换目的地后不残留旧路线。
- 未解锁、不可达、次数耗尽时显示真实原因，不出现“地图可选但现场无法使用且无解释”。
- 骑乘路线不穿墙、不穿树，不进入仅步行可过的窄缝；到达判定以真实交互范围为准。
- 图标 地点详情与垂钓界面指向同一地点，不出现多个同名点串场。

**拟涉及入口**　`RegionChestMap.gd`、`RegionMapPanel.gd`、`MapScene.gd`、`IllustratedNavigation.gd`、`data/main_world_maps.json` 及现场玩法入口。详见 C09。

## 五 统一复验要求

1. **固定测试版本**：每次记录安装包版本、设备、屏幕尺寸、系统栏状态、账号和关键存档条件。与附件截图比较时，说明测试场景和状态是否一致。
