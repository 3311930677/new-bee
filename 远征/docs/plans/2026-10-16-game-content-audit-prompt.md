# 游戏内容审查提示词

直接复制 §1 整段，粘贴给任意有文件读取能力的 AI 即可。想要专项审查，再追加 §2 的一段。

**审查对象**：`D:\new bee\远征`（Godot 4.7.2 / 480×800 竖屏 / 全 JSON 表驱动）
换项目时改路径即可，方法论通用。

## 1. 主体提示词（复制这一段）

```text
你是《远征》项目的资深技术美术 + 数值策划 + 工程审查员，三个身份同时在线。
请对 D:\new bee\远征 做一次游戏内容审查，产出一份报告。

===== 一、审查总原则（不许违反）=====

1. 文档即真相源。项目明文规定「代码是文档的实现」。所以任何「代码与文档不一致」
   都是缺陷，且要指出哪一边该改。先找文档定下的标准，再拿代码/实机去对。
2. 只写能证伪的结论。每条缺点必须带：编号、一句话结论、文件:行号 级证据、
   量化影响（MB / 像素 / 处数 / 帧 / 毫秒，能给数就给数）。
   没有证据的"感觉不对"只能写进「观察」，不能写进「缺点」。
3. 区分层次。发现必须标注属于哪一层：实现层 / 数据数值层 / 视觉层 /
   资源层 / 测试体系 / 文档一致性。不同层的问题不要混在一条里。
4. 商业美术质量不判。笔触、构图、艺术性留给独立美术复审。
   但要判"风格是否自洽"——同一个游戏里跑着几套视觉标准，是可客观判定的缺陷。
5. 不要只说缺什么。先给优点，且优点也要有证据（哪个文件、哪条数据、什么设计意图）。
   一份只列缺点的报告会被当作情绪输出。
6. 主动找"被回退的修复"。历次 review 声称已修的问题，要复验是否退回。
   被回退比原始缺陷更值得写——那是流程缺陷，说明缺自动化防复发。

===== 二、必须执行的检查（逐项做完再动笔）=====

A. 字号与排版体系
   - 从 src/autoload/G.gd 找到字号阶梯常量（FS_*）的定义值，并读它紧邻的注释。
   - 全项目扫描 add_theme_font_size_override("font_size", <字面量>)，
     排除 src/preview/（那是工具 UI 不是游戏 UI）。
     统计总数、取值频次分布、低于最小档的数量与明细。
   - 关键：字号有三条来源，grep 只能覆盖第一条——
     ① .gd 里的字面量；
     ② G.gd 工厂函数按参数动态传入（grep 扫不到）；
     ③ 实测渲染值（shots/rounds/*.text.json 的 text_nodes[].size）。
     所以必须用 .text.json 兜底，否则会漏报。
   - 拿 docs/ 里所有关于字号的表述与之对照，列出不一致的每一处
     （注释 vs 常量、文档 vs 代码，两个方向都要查）。
   - 读 .text.json 检查：是否有低于下限的字号、是否有 rect_height < height 的裁切、
     同一语义节点（如名签）在不同场景是否用了不同字号。
   - 反查可读性兜底机制：项目若有 src/ui/UIReadability.gd 这类东西
     （把 <24px 的艺术字自动降级、强制文字线性过滤），必须写进「优点」，
     并指出它一旦被漏调用会有什么后果。

B. 资源体积与引用
   - du -sh assets/*/ 列出各目录体积。
   - 对 fonts/ 逐个文件统计在 src/ 中的引用，标出零引用的。
     注意用 grep -rl 按文件计；grep -c 会把 const 声明和 load() 都算成引用，
     容易把"低频在用"误判为"闲置"。判闲置的标准是：除声明外无任何使用点。
   - 检查 assets/ 下的 *.log / *.stdout / *.stderr 构建垃圾。
   - 带日期的素材目录是历史批次快照，先 grep 是否被代码引用再判垃圾。

C. 数据表质量（抽样 data/*.json）
   - 是否每份都有 version。
   - 关键表（growth / equip / drops / economy / currencies / campaign_difficulty）
     的参数是否能互相印证（如掉落稀有度与装备模板权重是否对得上）。
   - 是否存在"注释说的"与"参数做的"不一致。
   - 难度/成长曲线是否单调、有无断层。

D. 视觉自洽性（看图 + 看配置）
   - 像素风内容与矢量风 UI 是否混用；纹理过滤策略是按目录设的还是按用途设的。
   - 主要母题（命名、纹样、字形）在核心场景间是否一致。
   - 名签/标签体系是否收敛为单一实现。
   - 是否存在跨分辨率验证（grep content_scale_factor；多尺寸截图）。

E. 工程与测试
   - 回归脚本规模与覆盖面。
   - 单文件体量异常（如某个 .gd 超过数千行）。

===== 三、报告结构（严格照此，不要自创章节）=====

0. 一句话结论
   —— 必须是可争论的判断，不许是"整体不错但仍有提升空间"这种废话。
1. 优点
   —— 编号 A1/A2/...，每条：结论 + 证据（文件/数据/行号）。
   —— 优先写"设计意图"类优点（数据表里主动防坑的注释、反刷设计等），
      这类比"代码写得整洁"有价值得多。
2. 缺点
   —— 编号 F-01/F-02/...，按严重度排序，标【严重】【中】【轻】。
   —— 每条严格三段：结论 → 证据（含 文件:行号 表格）→ 量化影响。
3. 改进方向
   —— 按 P0（可立即止血）/ P1（需设计决策）/ P2（长期）分组。
   —— P0 每一行必须有「验收方式」列，且是一条能跑的命令或一个可数指标。
4. 数据证据附录
   —— 命令原文贴上，实测结果写在注释里；附关键指标汇总表。
5. 审查范围声明
   —— 明确列出已覆盖与未覆盖。未覆盖的说明为什么、需要什么专项。

===== 四、格式硬要求 =====

- 编号：优点 A<n>、缺点 F-<nn>、改进 P<0|1|2>-<n>。编号一经使用不重排。
- 证据一律写 `路径:行号`，不用"某处""大概"。
- 量化用 MB / px / 处 / 个 / ms / 帧。
- 缺点明细、难度分组、字号对照、指标汇总一律用表格。
- 禁止"建议进一步优化""体验更佳"这类无法验收的措辞。
- 结论先行；单条缺点不超过 15 行；全文不超过 400 行。
- 落点：docs/plans/YYYY-MM-DD-<主题>-audit.md
```

## 2. 专项追加段（按需接在 §1 后面）

### 2.1 只审某一场景

```text
本次只审 <场景名>。其余场景不看，但要说明该场景与相邻场景的一致性。
重点：信息层级是否一眼可辨、最小字号、触控热区、状态反馈是否及时、
与其他场景共用组件的字号/尺寸是否一致。
```

### 2.2 只审数值平衡

```text
本次只审数值。对 data/ 下战斗相关表做组合空间分析：
怪物 × 图 × 难度档，找出极端组合（最脆/最肉/最高爆发），
判断是否存在某档位可被"无脑配置"绕过。给出具体怪物 id 与图 id。
不评价美术与 UI。
```

### 2.3 只审文档一致性

```text
本次只审文档与代码的一致性。对 docs/ 下所有 .md 与 docs/plans/ 下所有条目，
逐份提取其中"声称的数值/规范"，到代码与数据表里验证。
产出表格：文档行 → 声称值 → 实际值 → 判定 → 建议以哪边为准。
```

### 2.4 复验型（跑完一轮修复后）

```text
本次为复验。打开上一轮报告 <路径>，逐条确认状态：
已修复 / 仍存在 / 被回退 / 转为他因。
被回退的必须给出证据并升级为流程问题，提出 CI 级防回退方案。
不要重复列已修复项的优点，只报告变化。
```

## 3. 判据表：什么算缺点、什么算优点

| 现象 | 判定 | 依据 |
|---|---|---|
| 字号低于项目自定的最小档 | **缺点（严重）** | 项目自己的规范就是标准 |
| 同层信息在不同场景用不同字号 | **缺点（严重）** | 破坏视觉层级 |
| 常量值与紧邻注释不符 | **缺点（严重）** | 文档即真相源 |
| 文档说 A、代码做 B | **缺点（中）** | 同上，会导致后续接错 |
| 零引用资源 > 5 MB | **缺点（中）** | 直接体积成本 |
| 构建垃圾混在素材目录 | **缺点（轻）** | 会被导入链路吸收 |
| 只有单一分辨率验证 | **缺点（中）** | 上线风险零验证 |
| 像素风与矢量风同屏混用 | **缺点（中）** | 可客观判定的风格不自洽 |
| 历史 review 结论被回退 | **缺点（严重）+ 流程问题** | 说明缺自动化防回退 |
| 立绘风格与场景调性不符 | **缺点（轻）**，需美术决策 | 只判一致性不判艺术性 |
| 有可读性兜底机制 | **优点** | 用规则替代逐处手工；要指出漏调用风险 |
| 实测零文字裁切 | **优点** | 但要说清是被兜底机制守住的 |
| 数据表有防坑注释、数值单调 | **优点** | 主动设计 |
| 反刷/反滥用写进数据而非注释 | **优点** | 设计意图落地 |

## 5. 验收标准：用这份提示词产出的报告该长什么样

- [ ] 每条缺点都能指着某一个 `文件:行号` 说不一致在哪。
- [ ] 至少 3 条量化指标（MB / 处数 / px / 毫秒）。
- [ ] P0 每一项都有可直接执行的验收命令。
- [ ] 明确写出"被回退的历史修复"（若存在）。
- [ ] 有「审查范围声明」，说清哪些没做。
- [ ] 通读不出现"建议进一步优化"这类无法验收的措辞。
- [ ] 优点不是礼貌性铺垫，而是能被后续工作复用的设计资产。

## 6. 踩坑清单

1. **`.text.json` 的 `size` 是实测渲染字号**，比 grep 可信。字号有三条来源（见 §1 检查 A），只做 grep 会漏报 —— 实测的 20/26/36 就是 `G.gd` 工厂动态传入的。
2. **`src/preview/` 是工具 UI**，统计必须排除，否则虚高。
3. **`assets/` 下带日期的目录是历史批次**，先 grep 引用再判垃圾。`reference_complete_20261011` 就是在用的，只是旁边混了 30 个日志文件。
4. **`.gd.uid` 是 Godot 4 元数据**。`find -name "*.gd"` 不会匹配它，但 `ls | wc -l` 会 → 统计脚本数要用 find。
5. **`G.gd` 单文件 5800+ 行**，按需 `sed -n` 取段，不要整读。
6. **字体"引用数"要用 `grep -rl` 按文件计**。`grep -c` 会把 `const FONT_X := "path"` 和 `load()` 都算作引用，容易误判闲置。
7. **`UIReadability` 这类兜底机制会掩盖字号问题** —— 实机看起来"还行"不等于体系健康。审查要把"规范一致性"和"实机可读性"分开判：前者看数据，后者看截图，两者结论可能相反。
