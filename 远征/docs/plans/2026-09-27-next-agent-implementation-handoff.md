## 2. 执行原则与交付格式

每个任务包单独完成、验收、更新本文进度后再进入依赖它的下一包。每包要提交：玩家能做的完整操作链、相关数据表与代码、旧档处理、至少一张 480×800 真实 Godot 截图、对应场景操作记录、针对新增风险的测试，以及全量回归结果。只改 UI 原型、只加 JSON 数量或只写系统类，不能算完成。

变更尽量保持可回退：先写新服务，再让旧场景通过适配层调用；验证旧档和历练后移除旧分支。图像资产用明确的成品目录和资源 ID；新增像素图要在游戏内按实际显示尺寸检查透明边、脚点、遮挡和文字可读性。参考视频中的布局、节奏可以借鉴，内容名称和数值依照本作方案实现。

## 4. 各任务包的具体实施卡

### P00：锁定可复现基线（下一位 agent 第一件事）

1. 读总方案、联机附件和当前进度；记录 `git status`，标出本批未提交文件。保存现有 28 项回归结果和五张关键实机图：边城、古道、断碑坡、碑窟、碑窟首领战。不要把 `shots/` 的历史截图直接当现状。
2. 只复制匿名／测试存档做夹具：v1、v2、v3、新档各至少一份；缺少真实旧版样本时从 `VerifySave` 的迁移输入构造并标明“合成样本”。记录等级、钱包四币、材料、三槽装备投入、宠物、坐骑、主线步骤、地图位置和界碑历练局状态。测试不写真实 `user://save.json`。
3. 建一张差异清单：主街路宽、建筑和 NPC 站位、怪物等级标签、角色头顶名签、UI 字号、同图战斗宠物与目标信息。将视频每 2 秒抽帧后的**可证实观察**与设计提案分开写；未证实的原作公式标“未知”。
4. 输出 `docs/plans/...-baseline.md` 和截图索引，更新本文件的进度表。若原基线回归失败，先查运行环境与未提交工作，不能以删测试修绿。

### P01：主世界与战斗视觉样板、主城可走性

涉及：`data/main_world_maps.json`、`MapScene.gd`、`CityScene.gd`、`BattleScene.gd`、地区图与 `image/main_world/`。先定 480×800 同屏规范：地砖像素密度、角色／NPC／普通怪／首领显示高度、脚点、招牌与名签高度、主街最窄净宽、HUD 安全边距、按钮最小触控区、正文与次级字最小可读字号。把数值和四张标注截图写进风格样板；之后批量重绘按该样板验收。

顺序：重绘主城主街和左右店铺／NPC → 古道、断碑坡、碑窟地貌识别点和连续道路 → 战斗同图的地区光色、地面与效果 → 小图标／字体／弹窗。先复用方向、脚点正确的角色资源；不符样板的底图和怪物才重绘。实现主街全程可走、店门和 NPC 可点、出生安全，四张图都能看到出口方向。地图中央不能被大字、长任务条或散乱操作图标遮挡。

验收：实际新档从出生走到北门、进古道、进碑窟、返城，全程不穿墙、不被建筑／怪物堵住。480×800 截图逐张检查夜色／浅路／深地砖上的字体对比、怪物等级、角色昵称、宠物遮挡；触控设备上点击店门、NPC、战斗指令不误触。提交标注前后图与资源来源清单。

### P02：WorldSession、QuestService 与一次结算

现有 `G.story_event()` 只有顺序步骤和 `done[]`，`MapScene.gd` 同时承担刷怪、接战、奖励、切图与保存。新增服务时先定义以下稳定契约，场景只负责显示和交互：

```text
WorldEvent = {event_id, type, source_id, map_id, actor_id, payload, game_tick}
EncounterContext = {encounter_id, spawn_id, map_id, position, enemy_id, enemy_level,
                    return_position, story_source, rng_seed, status}
RewardTransaction = {transaction_id, costs, grants, world_flags}
```

`WorldSession` 管地图状态、唯一刷点、到达点、安全位置、怪物生命周期和遭遇锁；`QuestService` 只从事件推进目标；`RewardLedger` 或同职责模块按 `transaction_id` 一次扣除与发放金币、经验、物品和旗标。事件处理完毕才写档；重复战斗结果、重复 NPC 点击、重启重放只返回原结果。`BattleSim` 继续做规则层，`BattleScene` 继续做表现层。把 `s01`–`s12` 逐步迁移为新任务模型，旧档 `done[]` 映射到新目标状态，保留已领的奖励。

存档从 v3 升到 v4 前先设计字段与迁移报告；`SaveData.gd` 增加逐版迁移和语义校验，导入未来版本仍拒绝覆盖。崩溃点矩阵至少覆盖：开战前、战斗中、结算前、结算后未返回地图、切图写档中、交付任务物时、满包发奖时。每个点重新加载后只能有一种可解释状态，不能重复发物、丢任务物、把玩家放到怪物身上。现有主世界 `bosses_cleared`、`respawn_by_map`、`story` 必须迁移。

### P03：主世界战斗完整纵切

把战斗状态机明确为 `approach → locked → battle → result_pending → committed → return`。普通怪允许逃，回安全位并给短接触冷静期；剧情首领的撤退规则在按钮上写清。敌左我右、宠物站位稳定，四指令显示当前目标、技能等级／消耗／冷却／范围、道具数量与效果、逃跑后果。敌人蓄力有文字和图形两种预兆；失声碑灵做至少 2 个可观察、可应对的阶段或循环，加入反击窗口。第二首领先在 P05 内容阶段加入。

主城污染角落、古道、碑窟分别使用合理的地表与色调；战斗结束后恢复角色位置、朝向、镜头和地图怪物状态。`BattleSim` 的确定性与历练多怪编成不能被单怪世界战改坏。验收含胜、败、逃、药剂、换宠、托管、不同职业、断开进程后重载；同一 `result_id` 上报两次只结算一次。

### P04：装备实例、加工与旧档保值

先实现 `inventory.instances[]`（稳定 UID、模板、等级、稀有度、词条、强化、孔位、宝石、精炼、锁定），材料保持堆叠，任务关键物品单独分类不占 60 格普通背包。掉落、待领取箱、背包比较、可见换装、工坊三槽装备、确定性 3 合 1 宝石构成一条完整链。当前 `equip.json` 的三槽强化／宝石／精炼和旧钱包材料须等值迁移；不能无损映射的部分进入有明细的补偿，不做静默归零。

强化和加工界面显示输入、概率／保底、属性变化、失败后果；低阶保证成功。出售强化／稀有／锁定装备必须二次确认。验收：普通怪掉一件可装备物 → 比较 → 穿上后地图至少一处外观变化 → 强化／镶嵌 → 卸下／卖出；满包、缺钱、重复点击、读档、迁移再迁移的余额与物件 UID 均正确。

### P05：第一幕真正完成

保留目前 12 个稳定步骤，在 UI 聚合的章节节点下扩出目标类型 `collect / deliver / craft / choose / boss`。碑窟主线不只自动交物：铁匠处制作碑文提供两种等价材料路径和可预览的世界反馈；失败或材料不足不锁主线。为“失路兽”做第二个可选首领，有独立预兆、首胜奖励与重复战收益。六条支线按关系 2、生态／采集 2、商旅／价格 1、精英／秘闻 1 配置，至少一条选择改变 NPC 台词、环境和供货，而不挡主线。

第一幕还要补：角色第 2 技能与导师互动、剧情首宠岩龟、基础坐骑、定向保底装备、首个贸易订单、至少一件固定奇遇、碑窟结束后的地图／NPC 状态变化。安排四职业各跑一遍新档，从登录命名到复命计时，目标 30–45 分钟；记录死亡、回城、缺资源、任务方向误解点，再调等级与奖励。历练、签到、抽取不得成为通关必经条件。

### P06：四商品现货、工作和订单

第一幕已有一城两野，先把**边城市集、古道驿商、断碑营地**做成三个可走到的交易点，不用提前伪造第二／三座城；后续沉渊港、霜关驿接入同一贸易表。四商品为谷物、盐、药草、铁料，数据包含地区基础价、买卖差价、库存、运输负担、事件影响。以游戏内日结算，不依赖真实零点；同一存档种子、天数与世界旗计算出同一价格。界面显示近 5 次价格、已知影响因素、持有量和扣费后净收益。

稳定工作（搬运／修路／采药／送信）保证亏损后有恢复路线；有限订单绑定数量、目的地、过期规则和单次提交 ID。使用 P02 事务接口扣钱、扣物、发奖。建立批量模拟：同城反复买卖、零成本切图、背包满、订单重复提交、游戏内时间回退、读档重试、价格极端值，均不得复制物品或造成负余额。延期交割合约只在 III 幕且现货模拟通过后开发，单机第一幕不提前上线。

### P07／P08：扩大世界、统一画风、单机发布

按总方案的 II／III／IV 幕表逐城制作，不先批量生成空背景：每图至少一个地貌识别点、一个可记住的人或事件、敌人／采集特色和双向路径。先做沉渊港＋潮痕滩／旧盐道／水闸，再做霜关驿与商路／矿道／霜林／冰隘，再做渊口／界碑深处和结局。宠物蛋、两项特性与进阶、坐骑四向与窄路行为、钓鱼、关系事件、守碑誓约随幕开放；每加一系统就接入地图人物／地点／产出／消耗链，不新增只有菜单入口的养成条。
