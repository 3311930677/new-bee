# 《远征》全量修复与优化提示词（无人值守执行版）

> **用途**：把审查报告里的问题（含重构与体系改造）**一次性全量改完**，过程中不需要主人逐条确认。
> **前置**：先有一份审查报告（如 `docs/plans/2026-10-16-game-content-audit.md`）。
> **使用方式**：把 §1 整段复制给 AI。§2 是可选参数，首次跑建议保留默认值。

---

## 0. 这份提示词在设计上防什么

无人值守的自主改动，失败模式是固定的几种。这份提示词逐条对冲：

| 风险 | 对冲机制 |
|---|---|
| AI 改到一半卡住，留下半成品 | **分批 + 每批独立可验证 + 失败即回滚**（§1 三、四） |
| 改动破坏功能，但没人发现 | **每批完成后必须跑回归，非绿即回滚**（§1 四） |
| 改了代码忘了改文档（项目大忌） | **文档三同步检查写进验收条件**（§1 四） |
| 一次性改太多，无法定位问题 | **单批上限 + 逐项 commit**（§1 三、五） |
| 自主"优化"到无关代码 | **硬边界清单 + 禁止清单**（§1 二、六） |
| 回退了别人已修的东西 | **开工前先建基线快照**（§1 三·0） |
| 静默用错方式（如漏跑导入） | **固定命令序列**（§1 四） |

---

## 1. 主体提示词（复制这一段）

```text
你是《远征》项目的 autonomous 修复工程师。请读 docs/plans/2026-10-16-game-content-audit.md
（审查报告），把其中的问题**全量修复并优化**，包括必要的重构与体系改造。

本次任务**无人值守**：不要中途停下来问我"要不要继续"，不要逐条征求同意。
但"无人值守"不等于"无约束"——你必须在每一批改动后自我验证，验证不过就回滚。
遇到任何无法自主判断的情况，记录下来、跳过该项、继续下一项，最后统一汇报。

===== 一、开工前：建立基线与事实 =====

0. 先解析 Godot 可执行文件路径（不要猜、不要假设 godot 在 PATH 里）：
   读 远征/.godot/editor/project_metadata.cfg 的 executable_path；
   若读不到，再读 docs/开发规范.md 或问 tools/run_regression.ps1 的 -Godot 参数默认值。
   下文用 <GODOT> 指代它。当前实测值：
   D:/STEAM/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe
1. cd 到 D:\new bee\远征，确认 git 工作区状态。
   若有未提交改动，先 git stash 保存，记下 stash 名，收尾时恢复。
2. 记录基线 commit（git rev-parse HEAD），写进最终报告。
3. 跑一次全量回归，记录基线结果：
   powershell -NoProfile -File tools/run_regression.ps1
   必须记录：退出码、用例数、是否与 -Expected 一致。
   **基线非绿则停止全部改动**，直接把基线失败清单作为报告内容交付。
4. 读 docs/开发规范.md（§1 会话 SOP / §2 Git / §3 工程 / §6 验证清单）。
   这份文档的规则优先于你的一般判断。特别注意：
   - UI 一律走 G.gd 工厂，禁止自建配色/随手调参
   - 文档即真相源，代码是文档的实现
   - 禁止 git add -A / git add .

===== 二、改动边界 =====

【可以做】
- 修复审查报告里 F-01 ~ F-07 的全部问题
- 修复你在执行中**新发现的**同类问题（判据：能用 文件:行号 指出，且有量化影响）
- 重构：拆分超大文件、抽取重复逻辑、建立缺失的约束机制（如字号 lint）
- 体系改造：统一字号来源、统一名签实现、统一渲染过滤策略、补多分辨率验证

【绝对禁止】
- 改动玩法/数值口径（data/*.json 里的数值），除非报告明确指出数值错误
- 改动引擎/渲染/分辨率等不可变项（开发规范 §3.1 表格里的值）
- 引入新引擎版本或新第三方依赖
- force push、跳过 hooks、--no-verify
- 提交 .godot/、*.tmp、导出产物、密钥类文件
- 删除 assets/ 下带日期的历史批次目录（除非确认零引用——先 grep 再动）
- 为了让测试通过而修改测试断言（除-非断言本身写错了，且要在报告里举证）

===== 三、执行方式：分批 + 闸门 =====

0. 先建一份「回退锚点」：
   git tag auto-fix-baseline
   这就是全流程的后悔药。任何一批彻底失败时，可 git reset --hard auto-fix-baseline。

1. 把待修项排成批次。原则：
   - 每批 <= 3 个关联项（同一文件/同一主题归一批）
   - 按「低风险 → 高风险」排序：先做独立的清理类（删闲置资源、去构建垃圾），
     再做体系类（字号统一、lint 建立），最后做重构类（拆 G.gd）
   - 报告里的 P0 优先，但不是无脑优先——若 P0 依赖 P1 的决策，先做 P1

2. 逐批执行。每批的固定流程：
   a. 记录本批要改什么（文件 + 行号 + 改法）
   b. 改代码/数据/文档（三同步！见下）
   c. 跑验证（见 §四）
   d. 通过 → git add <具体文件> + git commit -m "<type>(<scope>): <中文描述>"
      不通过 → 回滚本批（git checkout -- <文件>），把失败原因记入报告的「未完成项」
   e. 进入下一批

3. **文档三同步**（项目硬规范，每次改动必查）：
   改了一处，必须检查另外两处是否要同步：
   - 玩法文档（口径）→ 提示词总库（素材 id）→ 代码/数据表（实现）
   本次重点：字号规范（docs 多份写 13/16/18/22/30/56，代码是 15/17/18/24/28/56）
   —— 统一到代码的实际值，把 docs 里的旧值全部改掉。

===== 四、每批的验证闸门（不可跳过）=====

按顺序跑，任何一步失败即本批失败：

1. 若新增了 class_name 的脚本，必须先跑导入（否则 headless 下 autoload 全废）：
   <GODOT> --headless --path 远征 --import
2. 语法/启动检查：
   <GODOT> --headless --path 远征 --quit
   要求：无报错、无红字（push_warning 可接受但要在报告里注明原因）
3. 若改了 UI/字体相关，**先找到项目当前的截图/文字审计采集入口**（不要自己新写）：
   查 shots/rounds/ 里 Version_X.Y_*.text.json 是由哪个脚本产出的
   （线索：tools/ 下有大量 Capture*.gd / Capture*.ps1；ls tools/ | grep -i capture）。
   复采后断言：
   - 无低于 FS_XS 的字号（排除 src/preview/）
   - 无 rect_height < height 的裁切
   若确实找不到可复用的采集脚本，**跳过本步并在报告里记录**
   （不要新写一套截图工具——那本身会成为新的技术债）。
4. 全量回归：
   powershell -NoProfile -File tools/run_regression.ps1
   必须：退出码 0 + 用例数与 -Expected 一致 + 无失败模式
   **回归脚本本身若被改动，额外跑**：
   powershell -NoProfile -File tools/selftest_regression.ps1
5. 若改了 data/*.json：确认全部可解析（UTF-8 无 BOM、2 空格缩进、无尾逗号）

判定口径（引用开发规范 §6）：每个用例必须 **退出码 0 + 打出自己的 <TOKEN>_OK 完成行
+ 无错误模式 + 在墙钟超时内结束**，且全程不得改写真实玩家存档。
"-Expected 不符" 一律视为失败。

===== 五、提交策略 =====

- 逐项提交：每批一个 commit，不要攒大包
- **不 push**。全部改完后停下，把结果交给主人确认（本次为「逐项提交，最后统一 push」）
- commit message 用 Conventional Commits + 中文，例如：
  fix(ui): 字号硬编码统一收敛到 G.FS_* 六档
  chore(assets): 清理 38 个构建日志与 1 个零引用字体
  docs(spec): 字号阶梯旧值 13/16/18/22/30/56 全部对齐到实际值
- 每批 commit 前用 git diff --stat 自查：改动范围是否与本批目标一致？
  若发现改了无关文件，回退重做。

===== 六、自主判断的准则 =====

遇到以下情况，**不要问、自己决策**：
- 两个文档冲突 → 以 docs/开发规范.md 为准，其次以代码实际值为准，并在报告里记录本次裁决
- 不确定是否该删某个资源 → 先 grep 引用；零引用且 >5MB 才删，否则跳过并记录
- 某项修复会牵连超过 5 个文件 → 拆成子批，或降级为「记录但不动」
- 修复方案有多种 → 选**改动最小、最不依赖推断**的那种

遇到以下情况，**跳过并记录，不做**：
- 需要美术决策（如"立绘风格统一到中式还是西式"）
- 需要主人给方向（如商业定位、付费设计）
- 无法用 文件:行号 定位的问题
- 改动会触及玩法数值口径

===== 七、收尾：产出交付报告 =====

在 docs/plans/ 下新建 YYYY-MM-DD-<主题>-autofix-report.md，包含：

1. 执行摘要：基线 commit、最终 commit、共几批、成功几项、跳过几项
2. 逐项状态表：| 报告编号 | 问题 | 状态(已修/跳过/失败) | commit | 验证证据 |
3. 端到端验证结果：最终回归的退出码 + 用例数 + 关键 TOKEN 行
4. **未完成项与原因**（这是最重要的部分，不要藏）
5. 自主决策记录：哪些地方是你自己裁决的、依据是什么
6. 回退说明：如何 git reset --hard auto-fix-baseline 回到开工前
7. 建议的人工跟进：需要主人拍板的事

最后：git status 确认状态，把「已逐项提交，待主人确认后 push」写进报告结尾。
不要 push。
```

## 3. 为什么必须「分批 + 闸门」

这份提示词的核心不是"让 AI 大胆改"，而是**让 AI 敢改的同时不炸**：

1. **回归套件是唯一的真相**。项目 `tools/run_regression.ps1` 的信任模型很严（退出码 + 专属 TOKEN 行 + 无错误模式 + 墙钟超时 + 存档哈希不变，`-Expected 77`）。它是无人值守能成立的前提——**没有它就别用这份提示词**。

2. **单批 <= 3 项**是为了让失败可定位。如果一批改了 20 个文件然后回归挂了，你不知道是哪一处；而回滚 20 个文件的改动又可能连带丢掉正确的部分。

3. **「失败即回滚 + 继续下一批」比「失败即停止」更好**。全量修复里必然有做不动的项（需要美术决策、需要主人拍板）。如果一项失败就整体停，那等于把无人值守退化成需要人盯。正确做法是：做不动的记录、跳过、继续。

4. **「不 push」是最后的保险**。所有改动都停在本地 + 有 tag 锚点，主人在任何时刻都能 `git reset --hard auto-fix-baseline` 一键回到开工前。push 是不可逆的，必须留给主人。

## 4. 已知风险（用之前要知道）

| 风险 | 现实评估 | 缓解 |
|---|---|---|
| 体系类改动（字号统一）触及几十个文件 | 中 | 拆成子批；先做 1 个场景验证流程，再铺开 |
| 拆分 `G.gd`（5800+ 行）回归挂掉 | **高** | 建议单独作为最后一批，且拆前先确认回归对 `G.gd` 的覆盖度 |
| 回归套件未覆盖的路径被改坏 | **中** | 无 CI 兜底，这是本方案最大的盲区。建议先补关键路径的回归，再跑全量修复 |
| 多分辨率改动无法验证 | 中 | 现状只覆盖 480×800，`content_scale_factor` 为 0。补多分辨率截图矩阵应作为独立批次，且需先有截图脚本 |
| AI 反复"优化"同一处 | 低 | 批次上限 15 + 每批必须 commit（有记录可查） |

**最重要的一条**：这个项目**没有 CI**。回归靠人手动跑。所以「无人值守」的天花板 = 回归套件的覆盖度。回归没覆盖的地方，AI 改坏了也没人知道。**跑这份提示词之前，值得先花一轮确认回归套件覆盖了你要动的那部分代码。**

## 5. 踩坑清单（会让流程直接失败的具体事项）

1. **Godot 不在 PATH 里**。必须从 `远征/.godot/editor/project_metadata.cfg` 的 `executable_path` 读，实测值 `D:/STEAM/steamapps/common/Godot Engine/godot.windows.opt.tools.64.exe`。直接写 `godot` 会报"不是内部或外部命令"。
2. **新增 `class_name` 的脚本必须先 `--import`**，否则 headless 下报 `Identifier "Xxx" not declared in the current scope`，autoload 全废。
3. **`run_regression.ps1` 是纯 ASCII 文件**，PS 5.1 会把无 BOM 的 `.ps1` 按 ANSI 读 → 不要顺手给它加中文注释，会让所有用例失败。
4. **`-Expected 77`**：新增/删除用例要同步改这个数，否则 runner 非零退出。只建文件不登记到脚本的用例表 = 不会被执行。
5. **不要用 `-Only` 跑通就算完**。无人值守的最后一次验证必须是**全量**（不带 `-Only`），单跑通过不代表整体通过。
6. **`git add -A` 被项目明令禁止**。必须逐文件 `git add <路径>`，否则会把 `.godot/`、导出产物、密钥一起提交。
7. **回归脚本隔离了玩家存档**（用临时 user_sandbox + 存档哈希校验）。若你的改动让"存档哈希变了"，会被判失败——那是真实缺陷不是误报。
8. **`assets/` 下有 38 个 `*.log/*.stdout/*.stderr`**，但**别用 `rm -rf`**；移出 `assets/` 即可，且先确认它们没被脚本引用为输入。
9. **`.text.json` 的 `size` 是实测渲染字号**，比 grep 可信 —— 字号有三条来源，grep 会漏。
10. **`G.gd` 5800+ 行**，读它用 `sed -n` 取段，不要整读。

## 6. 与另一份提示词的关系

| 提示词 | 干什么 | 何时用 |
|---|---|---|
| `2026-10-16-game-content-audit-prompt.md` | **找出问题**，产出审查报告 | 先跑这个 |
